🏨 KU HOME — คู่มืออัลกอริทึมจัดห้อง

อธิบายอัลกอริทึมจัดห้องทั้ง 5 ตัวของระบบ KU HOME พร้อมตัวอย่างมินิเดโม่แบบโต้ตอบ — กดเล่นได้เลยค่ะ!

📦 5 algorithms 🎮 Interactive demos 📚 Thai language 🔗 ← กลับ Playground

📋 Overview — ภาพรวมระบบ

ระบบ KU HOME ต้องจัดห้องให้ booking ที่ลูกค้าจองมา โดยแต่ละ booking อาจจะขอห้อง หลายประเภท (Suite, Deluxe, Superior) และอาจมี extra bed ด้วย เป้าหมายคือหาห้องที่:

  1. ว่าง ในช่วงวันที่จอง (ไม่มี reservation ทับซ้อน)
  2. ประเภทตรง กับที่ขอ
  3. อยู่ใกล้กัน ให้ลูกค้าเดินทางสะดวก (floor เดียวกัน, ฝั่งเดียวกัน, ตำแหน่งใกล้กัน)
  4. ไม่สูญเปล่า — เช่นไม่เอาห้อง 3 เตียงให้คนขอ 1 เตียงถ้ามีทางเลือกอื่น

💡 ทำไมต้องมีหลายอัลกอริทึม?

เพราะสถานการณ์การจองแตกต่างกันมาก — บางครั้งต้องการห้องติดกันแน่นๆ (กรณีกลุ่ม), บางครั้งต้องการ cost ต่ำสุด (กรณีทั่วไป), และบางครั้งต้องการความเร็ว (กรณีคิวยาวๆ) การมีหลายวิธีแล้วเปรียบเทียบ (Hybrid) จึงให้ผลลัพธ์ดีที่สุดค่ะ

🎯 นิยามปัญหา (Problem Definition)

Input

  • Booking = รายการห้องที่ขอ: [{type, beds}, ...] เช่น [{type:'Deluxe', beds:0}, {type:'Deluxe', beds:0}]
  • Dates = วันเช็คอิน/เช็คเอาท์: {checkIn, checkOut}
  • Rooms = ห้องทั้งหมดในอาคาร 100 ห้อง (20 ห้อง × 5 ชั้น)
  • Weights = น้ำหนัก cost: {floor, side, pos, bed}

Output

  • Assignments = ห้องที่จัดให้แต่ละ request: [room1, room2, ...]
  • Cost = คะแนน "ความไม่ดี" (ต่ำ = ดี)
  • OK/Fail = จัดได้ครบทุกห้องหรือไม่

เป้าหมาย

หา assignments ที่ cost ต่ำสุด โดยที่ทุกห้องใน booking ได้รับห้องที่ถูกต้องและว่าง ✅

💰 Cost Function — ฟังก์ชันคำนวณความแย่

ทุกอัลกอริทึมจะใช้ cost function ตัวเดียวกันในการประเมินว่าชุดห้องที่เลือกมา "แย่แค่ไหน" cost ต่ำ = ดี, cost สูง = แย่ โดยคำนวณจาก 4 ปัจจัย:

Floor Spread: (maxFloor − minFloor) × W_floor
Side Mismatch: (จำนวนฝั่งที่ต่างกัน) × W_side
Position Spread: Σ (maxPos − minPos ในแต่ละฝั่ง) × W_pos
Bed Waste: Σ max(0, roomBeds − 1 − requestedBeds) × W_bed
TOTAL COST: floorSpread + sideMismatch + posSpread + bedWaste
🏢 Floor Spread
×10
ชั้นห่างกัน = เดินลำบาก
🚶 Side Mismatch
×8
ฝั่งต่าง = ข้ามอาคาร
📏 Position Spread
×3
ห่างในฝั่ง = เดินไกล
🛏️ Bed Waste
×5
เตียงเกิน = สูญเปล่า

💡 ตัวอย่างคำนวณ

สมมติเลือกห้อง 508 (V1, pos 2) และ 612 (V1, pos 6):

  • Floor spread = (6 − 5) × 10 = 10
  • Side mismatch = 0 (ฝั่งเดียวกัน) × 8 = 0
  • Position spread = (6 − 2) × 3 = 12
  • Bed waste = 0 (ทั้งคู่ 1 เตียง ขอ 0 extra) × 5 = 0
  • TOTAL = 22 😐 (ปานกลาง)

เทียบกับเลือก 508 + 509: floor=0, side=0, pos=3, bed=0 → TOTAL = 3 ✅ (ดีมาก!)

น้ำหนัก W_floor=10, W_side=8, W_pos=3, W_bed=5 เป็นค่า default ที่เน้นว่า ชั้นต่างกันแย่สุด รองลงมาคือฝั่งต่างกัน เป็นต้น — ผู้ใช้สามารถปรับได้ในหน้า Playground ค่ะ

🔒 Overlap Filtering — กรองห้องที่ถูกจองแล้ว

ก่อนที่อัลกอริทึมจะเริ่มทำงาน ระบบจะ กรองห้องที่มี reservation ทับซ้อน กับช่วงวันที่ขอจองออกก่อน เพื่อไม่ให้เสนอห้องที่ไม่ว่างจริง

เงื่อนไข Overlap

Overlap เมื่อ: aIn < bOut AND bIn < aOut

คือ ช่วง [aIn, aOut) กับ [bIn, bOut) มีส่วนทับซ้อน แม้แต่ 1 วัน ก็ถือว่า conflict

⚠️ จุดสำคัญ

  • Check-out ของคนเก่าตรงกับ check-in ของคนใหม่ ไม่นับเป็น overlap (เพราะใช้ aIn < bOut ไม่ใช่ <=)
  • ห้องที่ถูก overlap จะถูก mark ว่า occupied และไม่เข้ากระบวนการเลือก
  • Step Explorer จะ log ห้องที่ถูกกรอง พร้อมเหตุผล เพื่อให้ debug ได้

🎯 X09 Priority Policy — สิทธิ์พิเศษห้อง 3 เตียง

เนื่องจากห้อง X09 (509-909) เป็นห้อง Deluxe 3 เตียง builtin เพียงไม่กี่ห้องในอาคาร ระบบจึงให้สิทธิ์พิเศษ: ถ้า booking มีคนขอ Deluxe + extra bed → เลือก X09 ก่อนเป็นอันดับแรก

📋 เงื่อนไขการทำงาน

  1. ตรวจว่า policy X09 priority เปิดอยู่ (default: เปิด)
  2. ตรวจว่า booking มี {type:'Deluxe', beds:>0} อย่างน้อย 1 ห้อง
  3. หาห้อง X09 ที่ ว่าง ในช่วงวันที่ขอ
  4. ถ้ามี → เลือก ชั้นต่ำสุด ก่อน (เช่น 509 ก่อน 609)
  5. จัด X09 ให้ request Deluxe+bed นั้น ก่อน ที่อัลกอริทึมจะทำงานต่อ

หลังจากจัด X09 แล้ว อัลกอริทึมจะทำงานกับ request ที่เหลือ เท่านั้น

🛟 Best-effort Fallback — เมื่อหาไม่ได้ก็ยังจัดให้

อัลกอริทึมบางตัว (A, B) มีเงื่อนไขเข้มงวด เช่น "ต้องติดกันจริง" หรือ "ต้องอยู่ใน component เดียวกัน" ถ้าหาไม่ได้ ระบบมี fallback:

🔄 กลยุทธ์ Best-effort

ถ้าเปิด policy best-effort (default: เปิด) เมื่ออัลกอริทึมหา block/component ไม่ได้ ระบบจะ:

  1. Sort ห้องว่างที่เหลือตาม floor → pos
  2. เลือกมาจัดให้ ตามลำดับ แม้จะไม่ติดกัน
  3. Mark ผลลัพธ์ว่า "best-effort" ใน step log

ผลลัพธ์อาจไม่สวย แต่ อย่างน้อยลูกค้าก็ได้ห้อง ดีกว่า fail ✅

🅰️ Algorithm A: Block Contiguous

A

Block Contiguous — หาห้องติดกันแน่นๆ

หากลุ่มห้องที่ pos ต่อเนื่องกันจริง บนชั้นและฝั่งเดียวกัน
✅ กลุ่มแน่นสุด ⚠️ อาจ fail ถ้าไม่มี block O(n×sides×floors)

📖 หลักการ

Algorithm A มองหาห้องที่ ติดกันจริงๆ คือ:

  • อยู่ ชั้นเดียวกัน
  • อยู่ ฝั่งเดียวกัน (V1 หรือ V2A หรือ V2B)
  • pos ต่อเนื่องกัน (เช่น pos 3, 4, 5, 6)

ถ้ามี block ที่ตรงเงื่อนไขหลายชุด จะเลือกชุดที่ cost ต่ำสุด

🔢 Pseudocode

// Algorithm A: Block Contiguous function algoBlock(booking): for each type in booking: available = filterAvailable(type) if available.length < needed: return FAIL // แบ่งตามฝั่ง for each side in [V1, V2A, V2B]: rooms = sortBy(available[side], floor, pos) // ลองทุก window ขนาด N for start in 0..rooms.length-N: block = rooms[start : start+N] // ตรวจว่าติดกันจริง if isContiguous(block): cost = costFunction(block) if cost < bestCost: bestBlock = block if bestBlock: return bestBlock else if bestEffort: return firstNAvailable(sorted) else: return FAIL

🅱️ Algorithm B: Graph Connected

B

Graph Connected — หากลุ่มใหญ่สุดด้วยกราฟ

สร้าง adjacency graph แล้วหา largest connected component
✅ ยืดหยุ่น ⚠️ ไม่รับประกันติดกัน O(n²) + BFS

📖 หลักการ

Algorithm B มองห้องเป็น กราฟ (graph) — แต่ละห้องคือ node และมี edge เชื่อมถ้า:

  • อยู่ ชั้นเดียวกัน
  • อยู่ ฝั่งเดียวกัน
  • pos ติดกัน (ต่างกัน 1)

จากนั้นใช้ BFS หา largest connected component (กลุ่มห้องที่เชื่อมกันได้ใหญ่สุด) แล้วเลือก N ห้องแรกจาก component นั้น

🔢 Pseudocode

// Algorithm B: Graph Connected Components function algoGraph(booking): for each type in booking: available = filterAvailable(type) // Build adjacency list adj = {} for i, j in available: if sameFloor and sameSide and |posDiff| == 1: addEdge(adj, i, j) // BFS หา connected components visited = {} bestComp = [] for room in available: if room not in visited: comp = BFS(adj, room) if comp.length > bestComp.length: bestComp = comp // เลือก N ห้องแรกจาก component ใหญ่สุด if bestComp.length >= N: return sort(bestComp)[:N] else: return bestEffort or FAIL

🅲 Algorithm C: Coordinate + Cost

C

Coordinate + Cost — คำนวณทุกชุด เลือกดีสุด

ลองทุก combination (ถ้าน้อย) หรือ greedy sort แล้วเลือก cost ต่ำสุด
✅ Optimal สุด ⚠️ ช้าถ้าเยอะ O(C(n,k)) brute

📖 หลักการ

Algorithm C เป็นวิธีที่ หนักแน่นที่สุด — มันพยายามหาชุดห้องที่ cost ต่ำสุดจริงๆ โดย:

  1. ถ้าจำนวนห้องที่ขอ น้อย (≤4) และห้องว่าง ไม่เยอะ (≤30) → brute force ลองทุก combination
  2. ถ้าเยอะเกิน → ใช้ greedy: sort by floor+pos แล้วเลือก N แรก
  3. เลือกชุดที่ cost ต่ำสุด

🔢 Pseudocode

// Algorithm C: Coordinate + Cost function algoCoordinate(booking): for each type in booking: available = filterAvailable(type) if N == 1: // เลือกห้องเดียวที่ cost ต่ำสุด best = sortBy(available, floor, pos)[0] else if N <= 4 and available <= 30: // Brute force! for each combo in combinations(available, N): cost = costFunction(combo) if cost < bestCost: bestCombo = combo else: // Greedy fallback sorted = sortBy(available, floor, pos) bestCombo = sorted[:N] return bestCombo

🔢 ทำไมต้องจำกัด brute force?

เพราะ C(30, 4) = 27,405 combinations — ยังพอไหว แต่ C(60, 5) = 5,461,512 จะ ช้ามาก ระบบจึงใช้ greedy แทนเมื่อเกินเกณฑ์

🅳 Algorithm D: Greedy Seed + Expand

D

Greedy Seed + Expand — เริ่มจากกลาง ขยายออก

เลือก seed ที่กลางสุด แล้วเพิ่มห้องใกล้สุดทีละจุด
✅ เร็วมาก ✅ ง่าย ⚠️ ไม่ optimal

📖 หลักการ

Algorithm D เป็นวิธี เร็วและง่าย — ทำงานเป็นขั้นตอน:

  1. เลือก seed: sort ห้องว่างทั้งหมด แล้วเลือกห้องตรง กลาง (index กลาง)
  2. Expand: เลือกห้องถัดไปที่ ใกล้ seed ที่สุด (คำนวณ distance = |floor diff| + |pos diff|×0.5 + side penalty)
  3. ทำซ้ำจนกว่าจะครบ N ห้อง

🔢 Pseudocode

// Algorithm D: Greedy Seed + Expand function algoGreedy(booking): for each type in booking: available = filterAvailable(type) sorted = sortBy(available, floor, pos) // 1. เลือก seed (กลางสุด) seedIdx = sorted.length / 2 seed = sorted[seedIdx] chosen = [seed] used = {seed} // 2. Expand ทีละจุด while chosen.length < N: candidates = available - used // เลือกที่ใกล้ seed ที่สุด best = minBy(candidates, lambda r: |r.floor - seed.floor| + |r.pos - seed.pos| * 0.5 + (r.side != seed.side ? 10 : 0) ) chosen.add(best) used.add(best) return chosen

⭐ Algorithm E: Hybrid (C+D)

E

Hybrid (C+D) — รันสองตัว เลือกคนชนะ ⭐ แนะนำ

รัน Coordinate (C) + Greedy (D) แล้วเลือก result ที่ดีกว่า
✅ Best of both ✅ Default O(C + D)

📖 หลักการ

Algorithm E เป็น meta-algorithm — มันไม่ได้คิดเอง แต่ รัน C และ D พร้อมกัน แล้ว:

  1. รัน Algorithm C (Coordinate + Cost) → ได้ resultC
  2. รัน Algorithm D (Greedy Seed + Expand) → ได้ resultD
  3. เปรียบเทียบ:
    • ถ้าทั้งคู่ OK → เลือก cost ต่ำกว่า
    • ถ้า OK อันเดียว → เลือกอันนั้น
    • ถ้า fail ทั้งคู่ → return fail

🔢 Pseudocode

// Algorithm E: Hybrid (C + D) function algoHybrid(booking): // รันทั้งสองตัว resultC = algoCoordinate(booking) resultD = algoGreedy(booking) // เลือกคนชนะ if resultC.ok and resultD.ok: if resultC.cost <= resultD.cost: return resultC // Coordinate ชนะ else: return resultD // Greedy ชนะ else if resultC.ok: return resultC // มี C คนเดียวที่ OK else if resultD.ok: return resultD // มี D คนเดียวที่ OK else: return FAIL // ทั้งคู่ fail

🌳 Decision Tree

if ต้องการ default ที่ดีที่สุด: → ⭐ Algorithm E (Hybrid) else if ลูกค้าเป็นกลุ่ม ต้องการติดกันแน่นๆ: → 🅰️ Algorithm A (Block) else if อาคารเต็มมาก (high occupancy): → 🅱️ Algorithm B (Graph) else if ขอห้องน้อย (1-4) และต้องการ optimal: → 🅲 Algorithm C (Coordinate) else if ต้องการความเร็ว คิวยาว: → 🅳 Algorithm D (Greedy) else: → ⭐ Algorithm E (Hybrid) — ปลอดภัยสุด

## บทคัดย่อ (Abstract)

รายงานฉบับนี้นำเสนอการเปรียบเทียบเชิงทดลองระหว่างอัลกอริทึม **ห้าตระกูล** เพื่อจัดสรรห้องพักให้กับการจองแบบกลุ่ม (group booking) ภายในโดเมนโรงแรมจำลอง **KU HOME** ซึ่งประกอบด้วยห้องพัก 100 ห้อง กระจายอยู่บน 5 ชั้น ภายใต้โครงสร้างฝั่งวิวและประเภทห้องที่มีข้อจำกัดเชิงกายภาพ (Suite/Deluxe/Superior วางอยู่คนละฝั่งของตัวอาคาร) อัลกอริทึมห้าตัวได้แก่ **A) Block Contiguous**, **B) Graph Connected**, **C) Coordinate + Cost**, **D) Greedy Seed + Expand**, และ **E) Hybrid (C+D)** ถูกทดสอบบนชุดทดสอบจำนวน **986 คู่กรณี** (34 สถานะเริ่มต้น × 29 กรณีการจอง) บวกกับการจำลองการจองต่อเนื่อง (online sequence) อีกกว่า 2,100 รายการ **โดยรวมกรณีที่แต่ละห้องใน booking เดียวกันมี check-in/out คนละช่วงกัน (per-room dates) อย่างชัดเจน** ซึ่งเป็นสถานการณ์ที่พบบ่อยในการจองกลุ่มจริง

ผลการทดลองชี้ให้เห็นว่า **อัลกอริทึม A และ B ซึ่งอ้างอิงโครงสร้างต่อเนื่อง (contiguity-based) ให้คุณภาพผลลัพธ์สูงสุดเมื่อสามารถหาบล็อกได้ แต่มีอัตราความสำเร็จเพียง 70.8% และ 62.9% ตามลำดับ** เนื่องจากข้อจำกัดทางโครงสร้างทำให้ไม่สามารถรองรับการจองหลายประเภทผสมหรือขนาดใหญ่ได้ ในขณะที่ **C, D และ E มีอัตราความสำเร็จ 100%** เนื่องจากไม่ผูกข้อจำกัดด้าน contiguity อัลกอริทึม **E (Hybrid)** ซึ่งทำงานโดยเลือกค่าต้นทุนต่ำสุดระหว่าง C และ D ให้ค่าต้นทุนเฉลี่ย 40.2 ซึ่งดีกว่า C (44.2) และ D (67.5) เมื่อพิจารณาเดี่ยว และไม่เคยให้ผลลัพธ์ที่แย่กว่าทั้งสองตัว **ในการทดสอบกรณี per-room dates โดยเฉพาะ E ยังคงครองอัตราความสำเร็จ 100% ทั้งใน single-case (C-PRD1..4) และ online sequence (SEQ11..13)** ดังนั้นรายงานฉบับนี้สรุปแนะนำให้ใช้ **E เป็นค่าเริ่มต้นสำหรับระบบจริง** และเสนอทางเลือกเพิ่มเติมคือการเพิ่ม A เป็นตัวตัดสินใจรอง (tie-breaker) เพื่อลดค่าต้นทุนได้ราว 31%

**คำสำคัญ:** การจัดสรรทรัพยากร · การหาค่าต่ำสุดแบบรวม (combinatorial optimization) · การจับคู่แบบทวิภาคี (bipartite matching) · ต้นทุนแบบไม่แยกส่วนได้ (non-separable cost) · **ความพร้อมต่อช่อง (per-slot availability)**

## 1. บทนำ

### 1.1 ที่มาและความสำคัญของปัญหา

การจัดสรรห้องพักให้กับกลุ่มผู้เข้าพักที่จองพร้อมกันหลายห้องเป็นปัญหาที่พบได้ทั่วไปในอุตสาหกรรมโรงแรม โดยเฉพาะในงานประชุม งานแต่งงาน หรือการจองแบบทีมงานบริษัท เป้าหมายคือการจัดห้องให้ **อยู่ใกล้กันทางกายภาพ** (เพื่อความสะดวกในการติดต่อและความปลอดภัย) ในขณะที่ต้อง **เคารพข้อจำกัด** หลายประการ ได้แก่ ประเภทห้องที่ผู้จองร้องขอ ความพร้อมของห้องในช่วงวันที่จอง และนโยบายเฉพาะของโรงแรม (เช่น การจองห้องเตียงเสริม)

ปัญหานี้จัดเป็นปัญหาการหาค่าต่ำสุดแบบรวม (combinatorial optimization) ซึ่งความซับซ้อนเพิ่มขึ้นอย่างมากเมื่อจำนวนห้องที่ต้องการจัดเพิ่มขึ้น เนื่องจากฟังก์ชันต้นทุนมีคุณสมบัติ **ไม่สามารถแยกส่วนได้ (non-separable)** — กล่าวคือ ค่าต้นทุนของห้องหนึ่งขึ้นอยู่กับห้องอื่น ๆ ที่จัดในการจองเดียวกัน (เช่น การกระจายข้ามชั้น) ทำให้เทคนิคคลาสสิกอย่าง Hungarian algorithm หรือ min-cost-flow ใช้ไม่ได้โดยตรง

### 1.2 วัตถุประสงค์ของการทดลอง

1. เปรียบเทียบอัลกอริทึม 5 ตระกูลบนชุดทดสอบเดียวกัน เพื่อหาจุดแข็ง-จุดอ่อนของแต่ละแนวทาง
2. วัดค่า **อัตราความสำเร็จ**, **คุณภาพผลลัพธ์ (ค่าต้นทุน)**, และ **เวลาประมวลผล**
3. เสนอแนะอัลกอริทึมที่เหมาะสมที่สุดสำหรับการนำไปใช้ในระบบจริง

### 1.3 ขอบเขตของการศึกษา

การทดลองนี้จำกัดอยู่ในโดเมน **KU HOME** ซึ่งเป็นโรงแรมจำลองขนาดกลาง (100 ห้อง) และไม่ครอบคลุมปัจจัยอื่น เช่น ราคาห้องพักแบบไดนามิก การยกเลิกการจอง หรือการปรับเปลี่ยนหลังจัดแล้ว (re-assignment)

## 2. โดเมนปัญหาและรูปแบบข้อมูล

### 2.1 โทโพโลยีของ KU HOME

โรงแรมจำลองประกอบด้วยห้องพัก 100 ห้อง กระจายบน 5 ชั้น (ชั้น 5, 6, 7, 8, 9) ชั้นละ 20 ห้อง โดยแบ่งออกเป็นสามฝั่งวิว:

```
ฝั่ง V1 (วิว 1 — 12 ห้องต่อชั้น):
  X07 (Suite, pos 1) · X08–X17 (Deluxe, pos 2–11) · X18 (Suite, pos 12)
  ⚠️ X09 = Deluxe 3 เตียง builtin (เฉพาะห้องเดียวที่ beds ≠ 1)

ฝั่ง V2A (วิว 2A — Superior 6 ห้อง):  X06, X05, X04, X03, X02, X01 (pos 1–6)
ฝั่ง V2B (วิว 2B — Superior 2 ห้อง):  X20, X19 (pos 1–2)

พิเศษ: ชั้น 8 ทุกห้องเป็นเตียงคู่ (bed_type = 'twin') · ชั้นอื่นเป็นเตียงเดี่ยวคู่ ('double')
```

โดยที่ `X` คือเลขชั้น เช่น `508` = ชั้น 5 ตำแหน่ง 2 (Deluxe), `809` = ชั้น 8 ตำแหน่ง 3 (Deluxe 3 เตียง twin)

### 2.2 รูปแบบข้อมูลห้อง (Room Object)

ห้องแต่ละห้องมีโครงสร้างข้อมูลดังนี้:

```js
{
  num: '508',           // เลขห้อง (string 3 หลัก)
  type: 'Deluxe',       // 'Suite' | 'Deluxe' | 'Superior'
  side: 'V1',           // 'V1' | 'V2A' | 'V2B'
  pos: 2,               // ตำแหน่งตามแนวเดิน (1–12 สำหรับ V1, 1–6 V2A, 1–2 V2B)
  beds: 1,              // จำนวนเตียง (1 ทุกห้อง ยกเว้น X09 = 3)
  floor: 5,             // ชั้น
  bed_type: 'double',   // 'twin' (ชั้น 8) | 'double' (ชั้นอื่น)
  reservations: [],     // รายการจองที่ซ้อนทับกับช่วงเวลาของห้องนี้
}
```

แต่ละการจองประกอบด้วยวันเช็คอิน/เช็คเอาท์ และรายการห้องที่ต้องการ:

## 3. ฟังก์ชันต้นทุน v2

เพื่อให้สามารถเปรียบเทียบผลลัพธ์ของอัลกอริทึมต่าง ๆ ได้อย่างเป็นภววิสัย (objective) ได้นิยามฟังก์ชันต้นทุนเดียวกันสำหรับทุกอัลกอริทึม โดยคำนวณจากผลรวมขององค์ประกอบ 5 ส่วน:

```
TOTAL = floorSpread + sideMismatch + posSpread + bedWaste + bedPrefPenalty
```

| องค์ประกอบ | สูตร | น้ำหนัก | ความหมาย |
|---|---|---|---|
| `floorSpread` | `(จำนวนชั้นที่แตกต่าง − 1) × W` | W=50 | การกระจายห้องข้ามหลายชั้น = แพงมาก |
| `sideMismatch` | `(ฝั่งวิวที่แตกต่าง − 1) × W` | W=8 | V2A และ V2B รวมเป็นฝั่ง V2 เดียว |
| `posSpread` | `Σ(max − min pos ของแต่ละฝั่ง) × W` | W=3 | การกระจายตำแหน่งภายในฝั่งเดียวกัน |
| `bedWaste` | `Σ max(0, beds − 1 − requested) × W` | W=5 | การใช้ห้อง X09 (3 เตียง) ให้การจองที่ไม่ต้องการเตียง |
| `bedPrefPenalty` | `Σ 100` ถ้า `bed_preference ≠ 'any'` และไม่ตรง | 100/ห้อง | เช่น ร้องขอ twin แต่ได้ double |

> ⚠️ **คุณสมบัติสำคัญ:** ฟังก์ชันต้นทุนนี้เป็นแบบ **ไม่สามารถแยกส่วนได้ (non-separable)** เนื่องจาก `floorSpread` และ `sideMismatch` ขึ้นอยู่กับห้องทั้งหมดในการจองร่วมกัน ดังนั้นเทคนิคการกำหนดการเชิงเส้น (linear assignment) อย่าง Hungarian algorithm จึงใช้ไม่ได้

## 4. อัลกอริทึมที่ทดสอบ

ทั้งห้าอัลกอริทึมรับอินพุตเดียวกัน (booking array) และคืนผลลัพธ์ในรูปแบบเดียวกัน แตกต่างกันที่กลยุทธ์การค้นหา

### 4.1 อัลกอริทึม A — Block Contiguous

**กลยุทธ์:** ค้นหาห้องติดกัน (contiguous) บนฝั่งและชั้นเดียวกัน โดยใช้ window scan ขนาด n และการจับคู่แบบทวิภาคี (bipartite matching)

- **จุดแข็ง:** เมื่อพบบล็อกจะให้ค่าต้นทุนต่ำสุด เพราะรับประกัน contiguity ทางกายภาพ
- **จุดอ่อน:** ต้องการห้องทั้งหมดอยู่ใน floor+side เดียวกันและตำแหน่ง pos ต่อเนื่องกัน +1 — ทำให้ล้มเหลวเมื่อ topology ไม่รองรับ (เช่น การจองผสม Suite+Deluxe+Superior)

### 4.2 อัลกอริทึม B — Graph Connected

**กลยุทธ์:** สร้างกราฟความใกล้ชิด (ห้องติดกัน = edge) แล้วหา largest connected component จากนั้น brute-force subset ขนาด n

- **จุดแข็ง:** ยืดหยุ่นกว่า A เล็กน้อยเพราะไม่ต้องการ window ต่อเนื่องโดยตรง แต่ยังต้องการ connected component
- **จุดอ่อน:** ต้องการ connected component ขนาด ≥ n ซึ่งหายากใน topology นี้ — จึงมีอัตราความสำเร็จต่ำที่สุด

### 4.3 อัลกอริทึม C — Coordinate + Cost

**กลยุทธ์:** คำนวณต้นทุนของทุกชุดค่าผสม (combinations) แล้วเลือกชุดที่ต้นทุนต่ำสุด มี gating เพื่อจำกัดการ brute-force เฉพาะเมื่อ `n ≤ 6 และ slotAvail ≤ 30` หากเกินจะใช้ greedy fallback

- **จุดแข็ง:** ครอบคลุมทุกกรณี (100% success) เพราะไม่ผูกข้อจำกัด contiguity
- **จุดอ่อน:** ช้าเมื่อ brute-force (สูงสุด ~4,600 ms เนื่องจาก C(30,5) = 142,506 ชุด) และอาจติดกับดััับ X09 penalty เมื่อเลือกห้อง 3 เตียง

### 4.4 อัลกอริทึม D — Greedy Seed + Expand

**กลยุทธ์:** เลือกห้องเริ่มต้น (seed) ที่ตำแหน่งกึ่งกลางของประเภทแรกที่ร้องขอ จากนั้นขยายไปยังห้องใกล้สุดที่เหลือตามระยะทาง Manhattan

- **จุดแข็ง:** เร็วที่สุด (ไม่ใช้ combinations เลย) และครอบคลุม 100%
- **จุดอ่อน:** ค่าต้นทุนเฉลี่ยสูงสุด เพราะ seed อยู่กลางแล้วขยายออกไปทำให้กระจายข้ามชั้นในเคสใหญ่

### 4.5 อัลกอริทึม E — Hybrid (C + D)

**กลยุทธ์:** รันทั้ง C และ D บนอินพุตเดียวกัน แล้วเลือกผลลัพธ์ที่มีค่าต้นทุนต่ำสุด

- **จุดแข็ง:** ครอบคลุม 100% เหมือน C/D และรับประกันว่าผลลัพธ์ไม่แย่กว่า C หรือ D ตัวใดตัวหนึ่ง
- **จุดอ่อน:** ช้าเท่ากับ C+D รวมกัน และยังพลาดบล็อกที่ถูกกว่าซึ่ง A เจอได้

## 5. ระเบียบวิธีทดลอง

### 5.1 การออกแบบชุดทดสอบ (Test Matrix)

ใช้โมเดลการประกอบ (compose model) ที่แยก **สถานะเริ่มต้น (seed)** ออกจาก **กรณีการจอง (case)**:

- **SEEDS:** 34 สถานะเริ่มต้น — จำลองห้องที่ถูกจองไปแล้วก่อนการทดสอบ
  - 7 แบบสร้างมือ (เช่น checkerboard, half-floor, premium-blocked)
  - 7 แบบอ้างอิง regression
  - 20 แบบสุ่ม deterministic (mulberry32 PRNG)
- **CASES:** 29 กรณีการจอง
  - 12 แบบเดี่ยวมาตรฐาน (single, วันเดียวกันทั้ง booking): ตั้งแต่ Solo (1 ห้อง) ถึง D20 (20 ห้อง — เป็นไปไม่ได้)
  - **4 แบบเดี่ยว per-room dates (C-PRD1..4)**: แต่ละห้องใน booking มี check-in/out คนละช่วงกัน
  - 10 แบบลำดับมาตรฐาน (SEQ1–SEQ10): จำลอง processQueue หลายรายการต่อเนื่อง
  - **3 แบบลำดับ per-room dates (SEQ11–SEQ13)**: แต่ละ booking ใน queue มี room ที่ date ของตัวเอง

ผลคูณ cartesian = **34 × 29 = 986 คู่** (ก่อน skip ที่ไม่เกี่ยวข้อง)

#### 5.1.1 รายละเอียดกรณี per-room dates (ใหม่ใน v2)

| Case | รายละเอียด |
|---|---|
| **C-PRD1** | Deluxe×3 โดย slot 2 คนละวันจาก slot 0,1 (baseline per-room date) |
| **C-PRD2** | Mixed (Suite+Deluxe+Superior)×4 ทุกห้องคนละวันกันหมด |
| **C-PRD3** | Deluxe×4 แบ่ง 2 cohort: 2 ห้องวัน A, 2 ห้องวัน B |
| **C-PRD4** | Deluxe×5 วันค่อย ๆ เลื่อน (staggered: T(1)→T(3), T(2)→T(4), …, T(5)→T(7)) |
| **SEQ11** | 3× Deluxe×3 ที่แต่ละ room ใน booking มี date ของตัวเอง (intra-booking per-room) |
| **SEQ12** | 4× mixed ที่ room บางตัว overlap กับ booking อื่นใน queue (intra+inter) |
| **SEQ13** | 5× Deluxe×2 ที่ date กระจายหลายช่วง (realistic multi-date group) |

### 5.2 สภาพแวดล้อมการทดสอบ

- ทุกอัลกอริทึมรันบนอินพุตเดียวกัน (same seed + case) เพื่อความเป็นภววิสัย
- ค่าน้ำหนักคงที่: `{ floor: 50, side: 8, pos: 3, bed: 5 }`
- การวัดเวลาใช้ `performance.now()` ของ Node.js
- นโยบายที่เปิดใช้: X09 priority, best-effort fallback

### 5.3 ตัวชี้วัด

1. **อัตราความสำเร็จ (Success Rate)** = จำนวนคู่ที่จัดห้องครบทุกช่อง / จำนวนคู่ทั้งหมด
2. **ค่าต้นทุน (Cost)** = ค่าจากฟังก์ชัน costFunction (ต่ำ = ดี)
3. **เวลาประมวลผล (Runtime)** = มิลลิวินาทีที่ใช้

## 7. ผลการทดสอบกรณี Per-Room Dates (เนื้อหาใหม่ใน v2)

> บทนี้ตอบคำถามสำคัญ: **เมื่อแต่ละห้องใน booking เดียวกันมี check-in/out คนละช่วงกัน อัลกอริทึมทำงานได้จริงไหม และตัวไหนดีที่สุด**

### 7.1 กลไกการจัดการ Per-Room Dates

เมื่อแต่ละ room ใน booking มี date ของตัวเอง ปัญหาจะซับซ้อนขึ้นเพราะ **availability ไม่ใช่ค่าเดียวทั้ง booking อีกต่อไป** — แต่ละ slot มี "availability mask" (เกราะ) ของตัวเอง สถาปัตยกรรมของ playground จัดการด้วยสามชั้น:

```
ชั้นที่ 1: brDates(br) — ดึงวันของ slot นั้น (fallback ไป booking-level)
   ↓
ชั้นที่ 2: isAvailableForBr(room, br) — เช็ค availability ต่อ slot
   (ห้องเดียวกัน "ว่างสำหรับ slot A" แต่ "ไม่ว่างสำหรับ slot B" ได้พร้อมกัน)
   ↓
ชั้นที่ 3: bipartiteMatch(adj) — แก้ปัญหา "ใครเอาห้องไหน"
   slot = ผู้ต้องการ, position = ห้องใน window/combo
   Edge = room.type ตรง + isAvailableForBr
   หา perfect matching = ทุก slot ได้ห้อง ไม่ซ้ำกัน
```

> ⚠️ **จุดสำคัญ:** ฟังก์ชัน `bipartiteMatch` (Kuhn's algorithm) เป็นกลไกที่ทำให้ระบบหลีกเลี่ยงกับดักแบบ "union availability" ได้ — กล่าวคือ ถ้าใช้วันรวม (union) เช็คทุกห้อง จะพลาดห้องที่ "ว่างเฉพาะบางช่วง" แต่ bipartite matching สามารถจับคู่ slot กับห้องที่ว่างสำหรับ slot นั้น ๆ ได้

## 8. การวิเคราะห์และข้อเสนอแนะ

### 8.1 การวิเคราะห์จุดแข็ง-จุดอ่อน

#### อัลกอริทึม A (Block Contiguous)
- **จุดแข็ง:** คุณภาพสูงสุดเมื่อสำเร็จ (เฉลี่ย 9.2) เร็วมาก
- **จุดอ่อน:** ล้มเหลวบนการจองผสมประเภทและขนาดใหญ่ (success 70%)
- **เหมาะกับ:** การจองห้องประเภทเดียวกันขนาดเล็ก-กลาง

#### อัลกอริทึม B (Graph Connected)
- **จุดแข็ง:** ยืดหยุ่นกว่า A เล็กน้อย
- **จุดอ่อน:** success rate ต่ำสุด (62%) และคุณภาพไม่ดีเป็นพิเศษเมื่อสำเร็จ
- **เหมาะกับ:** ไม่แนะนำให้ใช้เดี่ยว — มี A ที่ทำงานได้ดีกว่าในทุกด้าน

#### อัลกอริทึม C (Coordinate + Cost)
- **จุดแข็ง:** ครอบคลุม 100% ให้ผลลัพธ์ที่เหมาะสมที่สุดเฉพาะที่ (locally optimal)
- **จุดอ่อน:** ช้าเมื่อ brute-force (สูงสุด ~4,600 ms) และอาจโดน X09 penalty
- **เหมาะกับ:** เคสที่ความถูกต้องสำคัญกว่าความเร็ว

#### อัลกอริทึม D (Greedy Seed + Expand)
- **จุดแข็ง:** เร็วที่สุด ครอบคลุม 100%
- **จุดอ่อน:** ค่าต้นทุนเฉลี่ยสูงสุด (67.5) เพราะ greedy กระจายข้ามชั้น
- **เหมาะกับ:** เคสที่ความเร็วสำคัญกว่าคุณภาพ หรือเป็น component ของ hybrid

#### อัลกอริทึม E (Hybrid)
- **จุดแข็ง:** ครอบคลุม 100% คุณภาพดีกว่า C หรือ D เดี่ยวเสมอ
- **จุดอ่อน:** ช้าเท่ากับ C+D รวม และพลาดบล็อกที่ถูกกว่าซึ่ง A เจอ
- **เหมาะกับ:** ค่าเริ่มต้นสำหรับระบบจริง

### 8.2 ข้อเสนอแนะหลัก

> **🎯 แนะนำให้ใช้อัลกอริทึม E (Hybrid) เป็นค่าเริ่มต้นสำหรับระบบจริง**

ด้วยเหตุผลดังต่อไปนี้:

1. **อัตราความสำเร็จ 100%** — เท่ากับ C/D ที่ดีที่สุด ไม่มีความเสี่ยงที่จะปฏิเสธการจองที่จัดได้จริง
2. **คุณภาพไม่แย่กว่า component ใด** — เนื่องจาก E = min(C, D) จึงรับประกันได้ว่าผลลัพธ์ไม่เคยแย่กว่า C หรือ D ตัวใดตัวหนึ่ง (พิสูจน์จาก 0 ครั้งที่ E > C หรือ E > D)
3. **ผ่านการทดสอบ sequence 2,122 รายการ** — ครอบคลุมสถานการณ์ online ที่ระบบจริงต้องเผชิญ

### 8.3 ทางเลือกปรับปรุง (Optional Enhancement)

#### ทางเลือกที่ 1: E + A tie-breaker (แนะนำ)

เพิ่ม A เป็นตัวสมัครเพิ่มเติมในการตัดสินใจของ E:

```js
function algoHybridPlus(booking) {
  const c = algoCoordinate(deepCopy(booking));
  const d = algoGreedy(deepCopy(booking));
  const a = algoBlock(deepCopy(booking));
  const candidates = [c, d, ...(a.ok ? [a] : [])];
  const okOnes = candidates.filter(r => r.ok);
  return okOnes.length
    ? okOnes.reduce((min, r) => r.cost < min.cost ? r : min)
    : c;
}
```

| ตัวชี้วัด | E (ปัจจุบัน) | E + A tie-breaker |
|---|---|---|
| ความสำเร็จ | 100% | 100% (ไม่เปลี่ยน) |
| ค่าเฉลี่ย | 40.2 | ~28 (ใกล้ oracle 27.7) |
| เวลาสูงสุด | ~4.6 s | ~4.6 s (A เร็ว ไม่เพิ่มภาระ) |

#### ทางเลือกที่ 2: เพิ่ม time guard ใน brute-force

แก้ปัญหาความช้าของ C โดยเพิ่มการตัดการทำงานตามเวลา:

```js
// ใน algoCoordinate brute-force loop
const t0 = performance.now();
const MAX_MS = 500;
for (const combo of combos) {
  if (performance.now() - t0 > MAX_MS) break;
  // ... existing matching
}
```

จะลดเวลาสูงสุดจาก ~4,600 ms เหลือ < 500 ms โดยเสียคุณภาพเล็กน้อย

## 9. ข้อจำกัดของการทดสอบ

1. **ไม่รวมราคาห้องแบบไดนามิก** — ฟังก์ชันต้นทุนไม่พิจารณา revenue
2. **ไม่ทดสอบการยกเลิก/เปลี่ยนแปลง** — สมมติว่าการจองเป็นแบบ atomic
3. **Topology เฉพาะ KU HOME** — ผลอาจไม่ generalizable ไปยังโรงแรมอื่น
4. **ฟังก์ชันต้นทุนเป็นนิยาม** — ค่าน้ำหนักเป็นการตั้งค่านโยบาย ไม่ใช่ optimization แบบบริสุทธิ์
5. **ชุดทดสอบสุ่ม 20 seeds** — อาจไม่ครอบคลุม edge case ทั้งหมด (แต่เพียงพอสำหรับการเปรียบเทียบเชิงสัมพัทธ์)
6. **กรณี per-room dates ครอบคลุมแล้วใน v2** — ฉบับก่อนหน้า (v1) ไม่ได้ทดสอบ per-room dates จริง (เฉพาะ preset D1/D2/D3 ที่ผ่าน loadPreset) ใน v2 ได้เพิ่ม C-PRD1..4 (single) และ SEQ11..13 (sequence) เข้าสู่ matrix หลัก รวม 7 cases × 34 seeds = 238 คู่กรณี per-room dates จริง
7. **algoCoordinate ใช้ bipartite matching เฉพาะ n≤6 & slotAvail≤30** — เมื่อเกินเกณฑ์จะตก greedy joint fallback ซึ่งยังถูกต้องแต่คุณภาพอาจลดลง (เป็นข้อจำกัดของ gating ไม่ใช่ของ per-room date mechanism)

## 10. สรุป

การทดลองเปรียบเทียบอัลกอริทึม 5 ตระกูลบนชุดทดสอบ **986 คู่** (รวมกรณี per-room dates อย่างเป็นระบบ) แสดงให้เห็นว่า **ไม่มีอัลกอริทึมเดี่ยวใดที่เหนือกว่าในทุกมิติ** — อัลกอริทึม contiguity-based (A, B) ให้คุณภาพสูงเมื่อสำเร็จแต่ครอบคลุมต่ำ (70.8%, 62.9%) ในขณะที่อัลกอริทึม cost-aware (C, D) ครอบคลุมสมบูรณ์ (100%) แต่มี trade-off ระหว่างคุณภาพและความเร็ว

อัลกอริทึม **E (Hybrid)** ซึ่งผสม C+D เข้าด้วยกันให้สมดุลที่ดีที่สุดสำหรับการใช้งานทั่วไป: ความสำเร็จ 100% และค่าต้นทุนเฉลี่ย 40.2 ที่ไม่แย่กว่า component ใด ๆ **ในการทดสอบกรณี per-room dates โดยเฉพาะ (C-PRD1..4 + SEQ11..13) E ยังคงครอง success rate 100% และให้ค่าต้นทุนดีกว่า D ตั้งแต่ 22% ถึง 58%** ซึ่งยืนยันว่ากลไก bipartite matching + per-slot availability ของ playground ทำงานได้จริงในสถานการณ์ที่แต่ละห้องใน booking มี check-in/out คนละช่วงกัน การเพิ่ม A เป็น tie-breaker เสริมสามารถลดค่าต้นทุนได้ราว 31% โดยไม่กระทบความครอบคลุม จึงเป็นทางเลือกที่น่าพิจารณาสำหรับการนำไปใช้ในระบบจริง
